# Collectors

## Implemented in Desktop 0.2

Windows interactive-user collection is opt-in. On first launch the master switch is off, with CPU/RAM selected. Settings persist as collection.json in Tauri's application config directory. A malformed file starts collection off and displays a warning. Saving must succeed before a new configuration becomes active.

The worker samples selected sources at a nominal two-second period. CPU calls [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes); utilization is (delta kernel + delta user - delta idle) / (delta kernel + delta user). Kernel time includes idle. First reads, counter resets and long scheduling gaps establish a new baseline and leave CPU missing. On machines with more than 64 logical processors, this API measures the calling thread's primary processor group; multi-group aggregation is not implemented.

RAM separately calls [GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex), returning physical total and total-minus-available in bytes. Disabling CPU skips its OS call; disabling RAM skips its OS call. Disabling the master switch or selecting no sources suspends metric queries entirely. These choices control collection rather than discarding unwanted measurements after querying everything. No process enumeration is performed for metrics.

Accepted observations are committed to a local SQLite archive on the collector worker (WAL, FULL synchronization). The latest 1,800 observations also remain in memory, about one continuous hour, and are restored on startup. Pauses retain history; this ring limit does not expire or delete database records. Closing the client stops collection but retains committed history. Native Timeline reads one local day at a time, incrementally receives new rows, and supports date navigation, live following, selection analytics and range export. System metrics exports the recent ring. Web and browser preview retain demo providers. Autostart and an independent background agent are not implemented.

## Diagnostics and power tools

Foreground inspection is a one-shot request after a three-second delay to switch to the target window. It reads HWND, PID, window title and executable path via Win32, without elevation. Protected/exited processes may lack paths. PID/HWND are snapshot identifiers, not durable identities. Browser URL extraction requires a later UI Automation adapter and is explicitly unavailable; titles are never treated as URLs. Results remain on the Settings page and are not added to metric history.

In 0.2.1, Prevent automatic sleep uses [SetThreadExecutionState](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate) on one worker thread with ES_CONTINUOUS | ES_SYSTEM_REQUIRED only. It allows normal display timeout, resets off on restart, releases at exit, does not alter power plans, and does not prevent explicit manual sleep. It is an idle-sleep request, not a guarantee against all hardware, Modern Standby, battery or system policy transitions.

Manual display-off is disabled in 0.2.1 after a user reported repeated blackouts after wake and unexpected sleep. The old code broadcast SC_MONITORPOWER to all windows; it had no repeat timer, but broadcast delivery is not a reliable single-target action. Microsoft [warns against SendMessageTimeout with HWND_BROADCAST](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/28602-avoid-calling-sendmessagetimeout-with-hwnd-broadcast). The precise hardware sequence has not been reproduced. The native broadcast implementation and delayed task are removed, the UI button is disabled, and the legacy display_off IPC command immediately rejects without changing power state. No monitor-off request can be replayed on resume. The old requirement to disable sleep prevention before display-off was incorrect for the intended overnight-work use case and has been removed. Future reintroduction requires evidence of reliable one-shot behavior, normal input wake and continued system work; mock IPC checks cannot prove that.

## On-demand file usage

Utilities queries a selected file through the system Restart Manager DLL and reads its modified timestamp. Each request owns a session with RAII cleanup; list growth retries are bounded, work runs off the UI thread, and executable lookup matches process creation time. There is no process shutdown/restart, file-content access, permanent watcher or audit-policy change. This tool is independent of the metrics master switch. Results are best effort, not exhaustive file-handle or delete-blocker identification. Historical writer attribution is unavailable without pre-existing audit/event records; modification time alone cannot identify a program.

## Additional selective system sources

Network, disk, audio and media each have a persisted switch, defaulting off on first launch and when migrating older preferences. Only enabled sources are queried; a sample already in flight may finish after a setting change, but its result is discarded. Slow media calls run outside the shared configuration lock. Rate baselines/PDH queries reset on settings changes, disable and long gaps. COM/WinRT is initialized only for enabled output audio, input audio or media on the collector thread and released when all three are disabled or the worker exits.

Network uses [GetIfTable2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getiftable2) cumulative receive/send octets on up hardware interfaces. Rates are summed physical-adapter byte deltas divided by actual monotonic elapsed time. Loopback and virtual/VPN interfaces are excluded to reduce duplicate counting; this is not application traffic or exclusively Internet traffic. First reads, topology changes, counter resets and gaps over six seconds yield null. No adapter present produces an observed zero after warm-up.

Disk uses PDH English counter paths `\PhysicalDisk(_Total)\Disk Read Bytes/sec` and `\PhysicalDisk(_Total)\Disk Write Bytes/sec`, independent of Windows display language. A query is created lazily and closed on disable/error. Two snapshots are required; this measures physical-disk throughput, not process I/O or free disk space. Unavailable performance counters are reported as errors, never synthetic zeros.

Audio uses [IAudioMeterInformation](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudiometerinformation) on the current default multimedia render endpoint. The value is a sampled peak amplitude, scaled to 0–100, before endpoint volume attenuation; it is neither the volume slider nor a two-second loudness average. Software meters can report zero during exclusive playback. No waveform or raw audio is captured. Microphone endpoint levels use a separate opt-in input collector described below.

Now playing uses [Windows SMTC sessions](https://devblogs.microsoft.com/oldnewthing/20231108-00/?p=108980): current session title, artist, source app ID and playback status. This includes paused sessions, with status shown explicitly. Timeline renders playing intervals at full track height and paused intervals as a four-pixel strip at the bottom; hover preserves metadata and duration. The current reader calls GetCurrentSession, not GetSessions: only the system-selected session is archived, so other simultaneous registered players may be omitted. Missing metadata does not establish that an application has no SMTC support. This is separate from Core Audio session meters, which identify sound-producing processes without requiring song metadata. Only cooperating apps publish metadata; no song recognition, playback control, thumbnails or full listening-history reconstruction is implemented. Each WinRT async wait is capped at one second; missing sessions remain null, and API failures are shown separately. Media polling can add processing time to the nominal two-second cadence. Metadata remains local in SQLite, the recent ring and JSON export. Native Timeline derives estimated playing/paused intervals from adjacent snapshots, without filling gaps; it does not reconstruct activity before collection began.

## Windows display timeout

Utilities reads the active power plan with PowerGetActiveScheme and PowerReadACValueIndex / PowerReadDCValueIndex, and explicitly saves the two display timeout values using [PowerWriteACValueIndex](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powerwriteacvalueindex), PowerWriteDCValueIndex and PowerSetActiveScheme. Only GUID_VIDEO_SUBGROUP / GUID_VIDEO_POWERDOWN_TIMEOUT are written (seconds, zero = Never). Sleep and hibernation settings are never written; this is a persisted Windows plan setting, distinct from the temporary sleep-prevention request and the disabled manual display-off command.

Opening the page, changing a dropdown, refreshing or restarting does not write anything. Saving compares the original plan/values to current settings and refuses stale edits. Concurrent app saves are serialized. Partial failure attempts rollback and reports incomplete rollback explicitly; Windows does not provide an atomic transaction against outside power-plan edits. Access/group policy failures are surfaced without automatic elevation. Existing nonstandard timeout values are preserved; newly selected values are zero or 60–86400 seconds. Systems without batteries may still expose a DC plan value.

Native tests read real power settings only; all write/apply/rollback tests use fake policies. Actual policy writes, monitor wake behavior and OEM/Modern Standby interactions have not been hardware tested. These features use OS DLLs and the existing Windows Rust bindings; no runtime/driver is bundled, and release size has not been measured in this preview-only change.

## Deferred scope

GPU collection now has an opt-in switch. It lazily creates a Windows PDH query using English paths `\GPU Engine(*)\Utilization Percentage`, `\GPU Adapter Memory(*)\Dedicated Usage` and `\GPU Adapter Memory(*)\Shared Usage`. No vendor SDK, sensor driver, .NET runtime or subprocess is bundled. The Windows GPU performance counter provider requires compatible WDDM drivers; unavailable counters report errors and stay missing. The first collection establishes a baseline. Disable, settings changes, nonmonotonic timestamps and gaps over six seconds close the query and require a new baseline.

Engine instances are grouped by adapter LUID, physical GPU index and engine index. Process contributions to the same physical engine are summed and capped to 100%; each adapter's overall utilization is its busiest engine, not the sum of engines. Engines of the same type remain distinct. Only aggregated engine readings are archived; no process GPU readings are retained. DXGI supplies display names when available; counter identity remains available as fallback. LUID is a Windows session identity, not a globally durable hardware serial: a later boot may have different IDs. Adapter-memory counters supply already-aggregated dedicated/shared used bytes, not this application's DXGI memory budget. No GPU-memory capacity or resident/allocated equivalence is claimed. Buffer retries, adapter counts and engine counts are bounded; errors do not produce synthetic zero readings.

Battery and CPU frequency are separate opt-in sources, defaulting off for existing preferences. Battery uses GetSystemPowerStatus for presence, percentage, AC connection and charging flags. Unknown values remain nullable; a desktop without a battery can still have an AC state, and full/plugged-in does not mean charging. CPU frequency uses CallNtPowerInformation(ProcessorInformation) and records the arithmetic mean of Windows-reported CurrentMhz across logical processors. It is not effective per-core clock telemetry and may not reflect turbo behavior. Failed/zero reports remain missing. These use existing Windows Rust bindings and OS DLLs. Read-only native tests exercise available GPU arrays, battery status and frequency; no polling energy overhead or release-size measurement has been made. CPU temperature, sensor power, fans and per-process metrics remain deferred.

Foreground/context intervals, running-app lifetimes and AFK require separate collectors. Exact player-reported playback positions/events remain deferred. Prefer native UI Automation for browser/editor context without mandatory extensions. Privacy remains local-first: no keylogging, screenshots, raw audio or cloud upload.

## Archive operations

Settings shows the actual database path, committed row count and storage errors. A database-open failure leaves recent live readings available but Timeline reports the query failure; it never falls back to simulated measurements. Write failures retain the sample in memory and report the error, but failed samples are not queued for retry. The archive currently has no retention limit or automatic deletion. For a simple consistent manual backup, close the client before copying activity.sqlite3; copying only the main file while it is open may omit data in the WAL sidecar. No raw audio, screenshots or network payloads are stored. SQLite is statically bundled; no separate server or runtime installation is needed, and the release-size increase has not yet been measured.

## Application audio diagnostics

The Audio page inspects all active render endpoints, including non-default headphones, HDMI and routed outputs. It registers IAudioSessionNotification before calling GetSessionEnumerator/GetCount and maintains references to discovered sessions (see [Microsoft session enumeration guidance](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nn-audiopolicy-iaudiosessionenumerator)). A bounded agile-reference queue transfers notification references safely to one MTA worker. Session-instance identity is combined with endpoint ID, keeping separate sessions/devices distinct; processes are not deduplicated by PID. Metadata includes a best-effort display/executable name, creator PID, system-sounds status and multi-process marker. Shared sessions identify a creator, not every contributing program; system sounds cannot identify which program triggered a Windows notification. Browser sessions do not identify individual tabs.

Cached IAudioMeterInformation readings are sampled every 50 ms; ISimpleAudioVolume reads the session volume setting and mute status separately, without writing either. A peak at least 0.1 percent on a non-muted session updates the last-signal timestamp and retained peak. Values measure signal, not proof of an audible sound: endpoint mute/volume, drivers, exclusive mode and protected paths can affect audibility or meter availability. Null means unavailable, never fabricated zero. Very short sounds can occur between samples and be missed. Meters are not recordings; input devices are enumerated but microphones are never activated or captured.

The most recent signal and its peak remain visible for one minute even after the session ends. Recently ended entries expire; live quiet entries clear their recent-signal state after one minute. A retained peak is the maximum since the most recent uninterrupted recent-signal episode, not a rolling loudness average. Monitoring is independent of collection preferences, starts on first visit to Audio, continues across page changes/minimization, and can be paused explicitly. It does not recover sounds before it was started. Pause releases meters/managers and freezes the displayed result; app exit joins the worker. New app launches start idle. Reads/failed queries never change devices, master volume, per-app volume or mute. Output/device enumeration refreshes every second while running; unplugged devices and expired sessions release references.

Default multimedia and communications input/output names are shown. This version opens the documented [Windows sound settings URI](https://learn.microsoft.com/en-us/windows/uwp/launch-resume/launch-settings-app) for changes instead of implementing private default-endpoint COM policy interfaces. The URI is fixed, invoked only on explicit click, and receives no user-controlled command arguments. It is not an in-app default-device setter. Changes made in Windows are reflected on the next device refresh.

Diagnostics history stays in memory, outside SQLite and timeline collection. Per-output sessions are capped at 256, active endpoints at 64, notification queues at 256; limits appear as errors. Recently ended history is pruned to bound memory. No new third-party runtime, driver or Cargo package is added; release size remains unmeasured. Native tests use read-only snapshots and a uniquely identified silent WASAPI session initialized without starting playback, exercising session notifications without periodic enumeration. UI checks mock meters/device changes and the settings launch. Actual audibility, short-beep capture and device switching are hardware validation tasks.

## Application activity

Three independent switches (foreground/window, desktop app presence, idle) default off, including when loading older preferences. They share the collection master switch and nominal two-second cadence, and skip their respective OS queries when disabled. Foreground reads GetForegroundWindow, GetWindowTextW and the process executable path. Process identity uses PID plus GetProcessTimes creation time; unavailable identity is sample-specific to avoid merging recycled PIDs. Window HWND is a snapshot identifier, not a durable identity. No URL extraction, UI Automation, input hooks, keystroke logging or file contents are collected. Window titles may contain sensitive document names and are stored locally only when enabled.

Desktop app presence uses EnumWindows for visible, unowned desktop windows, including minimized windows; it excludes the shell desktop and groups processes by executable for the UI. This is not a complete list of background services or proof of background CPU work. Snapshots above 256 processes are omitted with an error, not silently truncated. Idle uses GetLastInputInfo in the current interactive session and a five-minute threshold; it does not establish sleep or absence. Short switches between snapshots may be missed. Activity intervals use bounded sample-and-hold support and never bridge missing observations. Historical activity from before opt-in cannot be recovered.

Native toolbar separates one-hour/day range from Live, which returns to today and follows the latest hour. Manual navigation pauses following. Week remains available in Demo; in native history it is shown disabled with an explanation until bounded multi-day queries and rollups exist. Charts retain raw line segments instead of smoothing away peaks.

## Help and storage controls

Audio application-session explanations and file-usage caveats remain available in keyboard-focusable, hoverable help tooltips. Display timeout controls use one row when space permits and wrap on narrow/high-zoom layouts, preserving the same explicit save/refresh behavior. Settings displays the estimated logical size of the SQLite database plus existing WAL/SHM sidecars (decimal MB); missing/unreadable size is unavailable rather than zero. Metadata reads do not query SQLite or checkpoint it. Open folder is a click-only native command that opens the configured database directory, accepting no frontend path or shell arguments. Close the app before copying the archive for backup.

## Audio-page media sessions

The Audio page independently scans GetSessions rather than GetCurrentSession, showing all returned playing/paused sessions with title, artist, source app ID and status. Playback is shown before paused entries. Leaving the page or pausing audio monitoring stops new metadata requests; cached results are retained in memory. The scan runs on a blocking IPC worker, separate from the fast Core Audio signal-meter worker. There is one native scan at a time, a 32-session limit, an overall two-second async-wait budget and a 350ms per-session metadata budget. Partial failures/limits are visible; refresh failures preserve the last result and mark it potentially stale. No thumbnails, audio recognition, player control, extra runtime or dependency are introduced. Apps that do not publish SMTC metadata cannot provide song information through this API; Core Audio remains the separate source for detecting their sound. Timeline/SQLite still archive the single system-selected media session, not this diagnostic list.

## Archive interval construction

Collector APIs and cadence are unchanged by schema 4. The storage transaction converts the existing foreground, desktop-app, selected SMTC-session and idle observations into normalized intervals; unchanged state extends a tail. Numeric readings remain samples. Background-window titles are not newly queried. Process instances use the collector's PID/creation identity, while Apps groups them by executable for display. State boundaries remain estimates with two-second final support, no interpolation across missing observations or writer restarts. See data-model.md for the physical schema and migration.

## Microphone level

A separate `audioInput` preference defaults off, including when loading older settings. Only an enabled input source under the master switch queries the default multimedia capture endpoint (`eCapture`, `eMultimedia`) through IAudioMeterInformation. Input-only collection keeps the collector COM apartment alive. Each cycle resolves the current default endpoint, so device changes are picked up on the next read. Missing devices, denied access and failed reads produce null with an Audio input error; valid zero remains zero.

Tracel only reads the Windows peak meter. It never initializes/starts an input audio client, obtains sample buffers, records audio, changes input gain or unmutes a microphone. Input peak is a 0–100 sampled amplitude before endpoint volume attenuation, not a two-second average or proof of actual speech. Idle input devices may return zero without an active capture stream; software meters also return zero during exclusive capture. Windows microphone policy and driver support can affect availability. The nominal two-second cadence can miss short sounds.

Schema 6 archives the nullable level, and native Timeline renders Audio input directly above Audio output under Audio & Media. Both use separate 0–100% lanes and independent sample-and-hold gaps. System metrics, Chinese labels, range analytics and JSON exports include input level. The on-demand Audio diagnostics page remains independent and does not start input streams. No new dependency, runtime or driver is bundled. Tests cover source isolation, unknown/zero readings, migration and COM lifetime; the native smoke query does not prove acoustic response on every microphone.
